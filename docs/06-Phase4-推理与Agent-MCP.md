## 三、关键讲解点

### ① 为什么 vLLM 快：三个核心机制

```text
LLM 推理的瓶颈不是"算得慢"，而是"显存管理差 + 调度差"
```

| 机制 | 解决什么问题 | 一句话理解 |
|---|---|---|
| **KV Cache** | 自回归生成时，前面 token 的 Key/Value 要反复用，不能重算 | 把"算过的注意力"缓存下来，占显存换时间 |
| **PagedAttention** | KV Cache 原来要预留连续大块显存，浪费 60~80% | 像操作系统的**虚拟内存分页**一样管理 KV Cache |
| **Continuous Batching** | 静态 batching 要等一批凑齐、等最慢的做完 | **每生成一个 token 就重新组批**：谁做完谁走，新请求随时插进来 |

### ② Continuous Batching 是什么感觉（M9-3 的核心收获）

你会看到这样的现象：

```text
并发 1  ：单请求延迟 0.9s，总吞吐 25 tokens/s
并发 16 ：单请求延迟 2.1s，总吞吐 260 tokens/s   ← 吞吐涨 10 倍！
```

**单请求变慢了，但总吞吐暴涨。** 这就是 continuous batching 在"用延迟换吞吐"，而且**换得非常划算**。

**这个现象你只能在 vLLM 上亲眼看到**（Ollama / LM Studio 看不到这么明显的效果）。这一张表，就是你面试时讲"我懂推理系统"的证据。

### ③ KV Cache 和 `max-model-len` 的关系（M9-5/6）

```text
KV Cache 显存 ≈ 2 × 层数 × 头数 × head_dim × 序列长度 × batch_size × 精度字节数
```

所以：
- `max-model-len` 调大 → 单条请求能吃更长上下文，但**每条约占更多显存** → 能并发的请求数变少
- 序列越长、并发越高 → 显存吃紧 → vLLM 开始排队（`pending`）而不是 OOM，这是它的调度策略

**8GB 显存会强迫你直面这个权衡——这反而是好事。** 有 80GB 卡的人不会去理解这个。

### ④ M9-2 那个瞬间

**你一行代码都没改，只加了一段 yml，网关就从"打远程 API"变成了"打自己跑的推理服务"。**

回去看一遍你的 `LlmProvider` 接口和 `ModelRegistry`。这就是 M3 坚持先立抽象、先不接真模型的回报。

**"面向接口编程"这句话你听过一百遍，今天你才真的信了。**

# M10：Agent Gateway（5 天）

> 从"网关转发一次请求"变成"网关编排一轮循环"。

## 一、Agent 和"直接调模型"的本质区别

```text
直接调模型：
  User → LLM → Answer                        （一次调用）

Agent：
  User → LLM → 它说"我要调用工具" → 你执行工具 → 把结果塞回去
       → LLM → 它又说"再调一个" → ... → Answer   （一个循环，N 次调用）
```

**Agent 的本质就是"一个由 LLM 决定何时停止的循环"。** 没有魔法。

## 二、任务卡

| 编号 | 任务 | 验收 |
|---|---|---|
| M10-1 | 读 OpenAI 的 `tools` / `tool_calls` 协议，手工构造一次带工具的请求 | 拿到 `tool_calls` 响应 |
| M10-2 | 实现一个本地工具（比如查时间 / 算除法 / 读本地文件），用 `@Tool` 风格注册 | 工具能被模型调用到 |
| M10-3 | 实现 Agent Loop：调模型 → 有 tool_calls 就执行 → 结果回灌 → 再调 | 模型能完成任务并给出最终答案 |
| M10-4 | 循环保护：最大步数 / 超时 / 重复调用检测 | 不会死循环烧钱 |
| M10-5 | 会话记忆：多轮对话 + 工具调用历史的拼接 | 上下文正确传给模型 |
| M10-6 | 流式 Agent：工具调用过程也流式暴露给客户端 | 用户能看到"正在查天气…" |
| M10-7 | 暴露成网关的一个入口（`/v1/agents/{name}/run`） | 通过网关调 Agent |
| M10-8 | 加一层"工具执行也要过网关治理"：权限、审计日志 | 每次工具调用都有审计记录 |

## 三、关键讲解点

### ① `tool_calls` 协议长什么样

```json
// 模型返回
{"choices":[{"message":{"role":"assistant","tool_calls":[
  {"id":"call_1","type":"function","function":{"name":"get_weather","arguments":"{\"city\":\"北京\"}"}}
]},"finish_reason":"tool_calls"}]}
```

然后你**把工具结果作为一条 `role: "tool"` 的消息塞回 messages**，再调一次模型：

```json
{"role":"tool","tool_call_id":"call_1","content":"北京晴，12℃"}
```

**这个"塞回去再调一次"的动作，就是 Agent 的全部秘密。**

> 注意 `arguments` 是**字符串形式的 JSON**（不是对象），且**模型可能生成非法 JSON**——你要做容错。这是新手必踩的坑。

### ② ReAct = Reasoning + Acting

```text
Thought（想）→ Action（调工具）→ Observation（看结果）→ Thought → ... → Answer
```

现在的大模型把这套内置进 tool calling 了，但**原理没变**：让模型"先想再动手，动手后看结果再想"。

### ③ Agent 网关的治理价值（M10-8）

这是你项目最值钱的一段叙事：

```text
如果让每个客户端自己实现 Agent Loop，会怎样？
  ❌ 工具权限散落在各处，无法统一治理
  ❌ 一个客户端写错循环，把 API 额度烧光
  ❌ 没有审计：不知道谁在什么时候调了什么工具、改了什么数据
  ❌ 工具实现重复：每个应用都要重新接一遍数据库/搜索/内部 API
```

**所以 Agent 和工具执行都应该收敛到网关。** 这正好对应你关注的 **AI & Agent Gateway Governance**。

**M10 结束时你要能讲清楚一句话**：为什么"网关"这个位置天然适合做 AI 治理？（提示：因为它**在数据流的必经之路上**——所有请求都从它过，所以它天然能鉴权、能审计、能限流、能拦截。这是位置决定的，不是功能决定的。）

# M11：MCP 治理（5 天）

## 一、MCP 解决什么问题

MCP（Model Context Protocol）本质是**"工具的 USB-C 接口"**：

```text
没有 MCP：每个 AI 应用都要为每个工具单独写一遍适配代码（M×N 问题）
有了 MCP：工具按 MCP 协议暴露一次，所有支持 MCP 的客户端都能用（M+N 问题）
```

## 二、任务卡

| 编号 | 任务 | 验收 |
|---|---|---|
| M11-1 | 读 MCP 规范：理解 JSON-RPC 2.0、`initialize` 握手、`tools/list`、`tools/call` | notes 里有一张协议交互时序图 |
| M11-2 | 手写一个最小 MCP Server（stdio 传输），暴露 1~2 个工具 | 能被 MCP Inspector 或客户端连上 |
| M11-3 | 实现 MCP Client：`initialize` → `tools/list` → `tools/call` | 能用代码调通自己的 Server |
| M11-4 | 网关托管 MCP：网关作为 MCP Gateway，统一代理多个 Server | 一个入口访问多个 Server |
| M11-5 | **工具命名空间**：多个 Server 的同名工具怎么区分 | 有清晰的命名/路由规则 |
| M11-6 | 权限模型：某个 API Key 只能访问白名单内的工具 | 越权调用被拒绝 |
| M11-7 | 审计：每次 `tools/call` 记录 谁/何时/哪个工具/参数摘要/结果状态 | 审计日志可查询 |
| M11-8 | 把 MCP 工具接到 M10 的 Agent Loop 里 | Agent 能调用 MCP 工具 |

## 三、关键讲解点

### ① 为什么"工具治理"是刚需

MCP 让工具接起来变容易了，但**风险也被放大了**：

```text
一个 MCP 工具可能是：读你的文件、查你的数据库、发邮件、执行命令
    ↓
谁来管"哪个用户能调哪个工具"？
谁来管"这个工具被调了多少次"？
出事了怎么追溯"是谁在什么时候用 Agent 删了表"？
```

**这就是 MCP Gateway 存在的理由。** 也是你这个项目从"玩具"变成"有工程价值的作品"的地方。

### ② 传输方式：stdio vs HTTP/SSE

| 方式 | 场景 | 特点 |
|---|---|---|
| stdio | 本地工具（同一台机器） | 简单，但进程隔离和权限控制靠宿主 |
| HTTP / SSE | 远程工具、多客户端共享 | **这才是网关能插手的地方** |

**网关能治理的前提是"流量从它这里过"。stdio 本地工具绕过了网关，所以治理必须在宿主侧做。** 这个区分你要能讲。

### ③ 最终的架构图（M11 结束时你应该能画出来）

```text
                       Client（ChatBox / 你的 App）
                                 │
                                 │ OpenAI 兼容 / MCP
                                 ▼
                    ┌─────────────────────────┐
                    │   Mini AI Gateway       │
                    ├─────────────────────────┤
                    │ 鉴权 / 限流 / 负载均衡   │
                    │ 路由（Model / Agent）    │
                    │ 可观测性（日志/指标）    │
                    │ 治理（权限/审计）        │
                    └───┬─────────┬───────┬───┘
                        │         │       │
              ┌─────────▼──┐  ┌───▼────┐  ▼
              │ LLM 路由层 │  │ Agent  │  MCP Gateway
              └──┬─────┬───┘  │  Loop  │  ├── MCP Server A
                 │     │      └────────┘  ├── MCP Server B
                 ▼     ▼                  └── MCP Server C
              Qwen  DeepSeek
                       │
                       ▼
                     vLLM ──▶ Local LLM
```

**这张图就是你的项目简历封面。** 从第 1 周的 `Client → Gateway → Backend` 长到这里，你走的每一步都有记录（git log）。
