## 一、为什么这时候才学 Redis

回看 M5 复盘第 6 题：你的网关重启会丢什么？

```text
内存里存的：限流计数、熔断状态、健康状态、统计数字
        ↓ 重启
      全没了
        ↓ 而且
   如果你起 2 个网关实例，各自算各自的，限流就形同虚设
```

**这就是你要 Redis 的原因——不是"Redis 很火所以学"，是"我的计数必须跨进程共享"。**

这就是《简介.md》里说的那种感觉：**是你自己的项目提出了问题，你才去学答案。**

## 关键讲解点

### ① 为什么自己写令牌桶

`Guava RateLimiter` 一行就够了。但**限流是分布式系统的入门仪式**，自己写一次，你会真正理解：

- 桶容量 ≠ 速率（容量决定**能攒多少突发**）
- 令牌是"按时间回填"的，不是定时器
- 单机版和分布式版的差别**只在"读改写"这一步**——单机是内存操作天然原子，分布式必须靠 Redis + Lua

**那个 Lua 脚本是你这一阶段最值钱的产出。**

### ② 为什么必须用 Lua（M6-5）

```java
// 错误示范：三步非原子
Long tokens = redis.get(key);        // 实例 A 读到 10
Long tokens2 = redis.get(key);       // 实例 B 也读到 10
redis.set(key, tokens - 1);          // A 写 9
redis.set(key, tokens2 - 1);         // B 也写 9  ← 少扣了一次！
```

并发下**竞态**必然发生。Redis 单线程执行 Lua 脚本，天然保证"整段原子"。

**你要能画出上面这个竞态时序图** —— 这是面试高频题。

### ③ 限流维度设计

| 维度 | 目的 | 例子 |
|---|---|---|
| 按 Key | 商业计费/配额 | 免费用户 5 QPM，付费 500 QPM |
| 按 model | 保护上游 | 贵的模型限得狠一点 |
| 按 IP | 防滥用 | 匿名接口 10 QPM |

**再想一层**：LLM 的"用量"其实不是 QPS，是 **token 数**。所以真正的 AI 网关要限的是 **TPM（tokens per minute）**。
QPS 限流只能防请求洪水，防不住"一个请求塞 10 万字 prompt"。**这是 AI 网关和普通 API 网关最大的区别之一** —— 试着实现一个 TPM 限流（提示：做完了才知道 token 得等响应回来才知道，所以要**预估 + 事后校正**）。

# M7：负载均衡与健康检查（4 天）

## 场景：上游从 1 个变成 3 个

```text
             Gateway
                │
      ┌─────────┼─────────┐
      ▼         ▼         ▼
   vLLM-1    vLLM-2    vLLM-3
```

（现在就可以用 3 个 `mock-backend` 实例（端口 8081/8082/8083）来练，**不需要等 vLLM**。每个实例 echo 时返回自己的端口，你就能看出请求被分到哪了。**这是个很关键的练手技巧：不要让基础设施挡住你练算法。**）

## 任务卡

| 编号 | 任务 | 验收 |
|---|---|---|
| M7-1 | 起 3 个 backend 实例（端口不同），echo 里返回自己的端口 | 能看出分流 |
| M7-2 | 轮询（Round Robin） | 3 个实例依次收到请求 |
| M7-3 | 加权轮询 / 加权随机 | 权重 2:1:1 时大致符合比例 |
| M7-4 | 最少连接数（Least Connections） | 流式长请求下比 RR 更合理，能说出为什么 |
| M7-5 | 被动健康检查：连续失败 N 次 → 摘除，冷却 M 秒后试探恢复 | 杀掉一个实例，请求不再打到它 |
| M7-6 | 主动健康检查：定时探 `/actuator/health` | 实例恢复后自动加回 |
| M7-7 | 重试 + 换实例：一次失败后换另一个实例再试一次 | 一个实例挂掉，用户无感知 |
| M7-8 | 一致性哈希 vs 无状态：**写一段你的思考** | notes 里有一段"为什么 AI 场景下不一定用一致性哈希" |

## 关键讲解点

### ① 最少连接数为什么对流式更友好（M7-4）

轮询假设"每个请求成本一样"。但 LLM 请求**差异极大**：一个 50 token 的回答和一个 4000 token 的回答差 80 倍。

轮询会把长请求全压到同一个实例上，而最少连接数（Least Connections / Least Outstanding Requests）会自然把新请求给"正在忙的程度最低"的那个。

**这个认知只有你压测过之后才会真的信。** 所以 M7 一定要压测。

### ② 被动 vs 主动健康检查

| 类型 | 怎么工作 | 优点 | 缺点 |
|---|---|---|---|
| 被动 | 从真实请求的失败里学 | 零额外开销，反映真实体验 | 发现慢，用户先被坑 |
| 主动 | 定时探活 | 发现快 | 探活成功 ≠ 业务正常 |

**生产上两个都要。** 你要能解释"探活接口返回 200，但模型加载失败导致业务全挂"这种场景——所以健康检查要检**依赖**，不只是"进程活着"。

### ③ 思考题：AI 场景要不要一致性哈希？

普通缓存场景，一致性哈希能提高缓存命中率。
但 LLM 场景有意思的地方是：**vLLM 有 prefix caching（前缀缓存）**。如果两个请求的 prompt 前缀相同（比如同一个 system prompt），打到同一个实例上就能复用 KV Cache，快很多。

**所以"亲和性路由"在 AI 网关里又变得有意义了，但理由和缓存完全不同。**

这就是《简介.md》里说的"每增加一个模块，就对应一个新的知识领域"。**这个问题你现在答不好很正常，M9 做完 vLLM 后回头答。**

| M8-4 | 起 Prometheus，抓你的网关 | Prometheus 里能查到指标 |
| M8-5 | 起 Grafana，画一张面板：QPS / p50·p95·p99 / TTFT / 错误率 / token 速率 | 面板能反映真实流量 |
| M8-6 | 埋点对比实验：并发 1 / 8 / 32 压测，截图对比 p95 变化 | 有一张自己的压测曲线 |

| M8-8 | 写一份 `docs/BENCHMARK.md`：把你的压测数字整理成表格 | 简历上的核心素材 |

## 关键讲解点

### ① 为什么必须是结构化日志（M8-1）

```text
❌ 2025-01-01 12:00:00 请求完成 耗时1200ms
✅ {"ts":"...","traceId":"a1b2","model":"qwen","provider":"dashscope",
    "latencyMs":1200,"ttftMs":340,"promptTokens":850,"completionTokens":420,"status":200}
```

**理由**：日志是**数据**，不是给人读的散文。结构化之后你才能：
- 统计"qwen 今天的平均延迟"
- 报警"错误率 > 5%"
- 排查"某个用户的请求为什么慢"

### ② AI 网关必须盯的独有指标（M8-3）

普通网关看 QPS / 延迟 / 错误率。AI 网关还要多盯：

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| **TTFT** | 首 token 延迟 | 用户"感觉快不快"几乎完全取决于它，而不是总延迟 |
| **TPOT / ITL** | 出字速度（tokens/s） | 决定"读起来流不流畅" |
| **prompt / completion tokens** | 用量 | **这就是钱** |
| **上游 vs 网关自身耗时** | 定位是谁慢 | 网关慢和模型慢，处理方式完全不同 |
| **被限流次数** | 容量判断 | 决定要不要扩容 |

**你要能解释：为什么"平均延迟 1.2s"这句描述毫无价值，而 p95 才有价值。**
（提示：平均值会被大量快请求拉低，掩盖长尾；而用户骂的永远是长尾。）

### ③ "上游慢"和"网关慢"怎么区分

在网关里分别打点：
```text
网关自身耗时 = 总耗时 - 上游耗时
```
如果网关自身耗时很高 → 你的代码有问题（序列化？日志？锁？）
如果上游耗时高 → 模型服务的问题

**这个减法意识，是从"会写代码"到"会运维系统"的分界线。**
